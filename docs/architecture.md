# Архитектура

## Назначение

Приложение — self-hosted browser IDE для одного server-configured LikeC4 workspace. Браузер получает данные только через HTTP API backend и не имеет доступа к файловой системе хоста.

## Границы REQ-01

REQ-01 создаёт только runnable app shell. `WorkspacePort` скрывает filesystem provider за интерфейсом. В этот срез не входят configured workspace, файловые операции, Monaco, parsing, diagnostics или diagram renderer.

Каждая панель запрашивает собственный HTTP resource и самостоятельно показывает loading, empty, ready или error state. Ошибка панели не должна заменять весь экран.

## Границы REQ-02

REQ-02 делает workspace server-configured. `loadServerConfig` (`apps/server/src/config.ts`) читает `LIKEC4_WORKSPACE` и `PORT` до построения приложения и проверяет каталог: существует, является directory и читаем процессом. При пустом, отсутствующем или недоступном значении startup завершается однострочной понятной ошибкой; сообщения называют только значение оператора, а не resolved-пути хоста. `PORT` по умолчанию — безопасное непривилегированное `3000`.

`LocalWorkspaceProvider` (`apps/server/src/adapters/local-workspace.ts`) — единственная реализация `WorkspacePort`; placeholder REQ-01 `EmptyWorkspaceProvider` и статус `unconfigured` удалены, так как сервер без валидного workspace больше не стартует. `GET /api/workspace` возвращает только `status` и `displayName` (basename нормализованного configured-пути; symlink-цель и абсолютный путь хоста не раскрываются). HTTP API не имеет параметров выбора workspace path.

`listFiles` и `getDiagram` на этом срезе оставались placeholder'ами (реализованы в REQ-04 и REQ-15). Новые upstream-зависимости не добавлены: используется только `node:fs`.

## Границы REQ-03

REQ-03 вводит единственный path guard файловых операций — `WorkspacePathResolver` (`apps/server/src/workspace-paths.ts`). `LocalWorkspaceProvider` владеет им как единственной точкой резолюции; файловые операции REQ-04–REQ-11 (list, read, write, create file, mkdir, rename, delete) принимают от клиента только относительный путь и резолвируют его исключительно через этот resolver. Два режима: `resolveExisting` (read, delete, источник rename) проверяет realpath самой записи; `resolveChild` (write, create, mkdir, назначение rename) — realpath parent, а если запись уже существует, то и её realpath. List строится обходом от доверенного корня без клиентского пути.

Проверка двух уровней. Лексическая: путь проверяется после URL-decoding и после нормализации — `..`, абсолютные пути (posix и windows-формы) отклоняются до любого обращения к fs, NUL и `\` считаются запрещёнными символами. Физическая: realpath проверяемой цели обязан находиться внутри realpath workspace root, поэтому symlink наружу не проходит; внутренние symlink разрешены, клиенту отдаётся реальный относительный путь. Повторное декодирование сознательно не выполняется: значение, пришедшее дважды закодированным, остаётся литеральным именем и заканчивается 404, не становясь traversal.

Коды ошибок (`packages/contracts`): `INVALID_PATH` 400 (malformed-путь), `PATH_OUTSIDE_WORKSPACE` 403 (traversal, абсолютный путь, symlink наружу), `NOT_FOUND` 404 (несуществующая запись или parent) — все варианты дают 4xx через общий error envelope. Сообщения называют только путь, присланный клиентом; абсолютные пути хоста, realpath-цели и содержимое внешних файлов не раскрываются. Runtime-код не выполняет shell-команд и не использует `child_process` (единственный вызов — startup-тест REQ-02, который запускает сам сервер фикс-командой без пользовательских данных), поэтому пользовательский DSL и пути в shell не попадают.

Известное ограничение: проверка realpath и последующая файловая операция — не одна атомарная транзакция (существует TOCTOU-окно). MVP работает в доверенной single-user среде, поэтому это принято сознательно. Новые upstream-зависимости не добавлены.

## Границы REQ-04

REQ-04 делает навигацию по разрешённым файлам реальной. `GET /api/files` строит дерево обходом от доверенного realpath-корня resolver’а REQ-03 (`listWorkspaceFiles`, `apps/server/src/workspace-tree.ts`); клиентский путь в endpoint’е не участвует, query-параметры игнорируются. Каждая запись проверяется по realpath: symlink наружу workspace не попадает в дерево (критерий «дерево не содержит entry за границами workspace»), внутренние symlink разрешены, а realpath посещённых каталогов запоминается — циклы symlink не зацикливают обход, и каталог показывается один раз. Недоступный для чтения подкаталог пропускается, не ломая всё дерево; ошибка чтения самого корня даёт общий 500 error envelope.

Правила фильтрации живут в одном модуле `apps/server/src/domain/allowed-files.ts` и обязательны для списка; endpoint чтения (REQ-05) будет использовать тот же классификатор, поэтому список и чтение не могут разойтись. Разрешены: LikeC4-исходники с расширениями `.c4` и `.likec4` (без учёта регистра) и конфигурационные файлы LikeC4 — состав имён зафиксирован документацией upstream v1.59.4 (`apps/docs/src/content/docs/dsl/Config/index.mdx`): `.likec4rc`, `.likec4.config.json`, `likec4.config.json`, `likec4.config.js`, `likec4.config.mjs`, `likec4.config.ts`, `likec4.config.mts`. Классификация идёт по имени записи без анализа содержимого: бинарные и нерелевантные файлы (`README.md`, `package.json`, изображения) не предлагаются как редактируемый DSL. Скрытые записи (`.git`, `.DS_Store`) не попадают в дерево, кроме config-файлов LikeC4, которые сами начинаются с точки. Каталоги без разрешённых файлов вырезаются вместе с веткой; единственное исключение введено REQ-09 — физически пустой каталог виден как directory-entry без детей, иначе созданный каталог не появился бы в дереве.

Ответ — плоский детерминированный список `FileEntry` (контракты не менялись): только workspace-относительные пути с `/`-разделителем, каталоги первым уровнем следуют перед файлами, каждый список отсортирован по имени, за каталогом сразу идёт его содержимое. Абсолютные пути хоста в ответе отсутствуют. Frontend (`buildFileTree`) восстанавливает вложенность из путей: Files panel показывает каталоги и файлы с различимыми метками `C4`/`CFG` (`data-language`), клик по файлу — это selection по относительному пути, который Code Editor panel показывает как открытый файл; никаких новых HTTP-запросов при этом не возникает. Новые upstream-зависимости не добавлены: обход использует только `node:fs/promises`.

## Границы REQ-05

REQ-05 делает открытие файла реальным: `GET /api/files/*` (wildcard рядом со списком `GET /api/files`) возвращает буквальный UTF-8 текст разрешённого файла и стабильный version token текущего содержимого. Чтение — `readWorkspaceFile` (`apps/server/src/workspace-file.ts`): путь проходит только через `resolveExisting` guard REQ-03 (realpath цели внутри workspace), поэтому traversal, абсолютные пути и symlink наружу отклоняются до открытия; literal `..` дополнительно схлопывается самим router’ом (find-my-way) до 404. Тип проверяется общим классификатором REQ-04 по базовому имени запрошенного пути — тому же правилу, по которому файл попал в дерево, поэтому список и чтение не расходятся.

Содержимое не преобразуется: bytes читаются как есть, декодируются строгим UTF-8 decoder’ом (`fatal`, `ignoreBOM` — BOM сохраняется в тексте), а бинарность отвергается по NUL-байту или невалидной UTF-8 последовательности — оба случая дают `UNSUPPORTED_FILE` 415 (новый код в контрактах), как и запрещённый тип (`README.md`, изображения). Каталог, названный как исходник, отклоняется `INVALID_PATH` 400. Version token — sha256 от исходных bytes: стабильный для одинакового содержимого, меняющийся при любом изменении; отдаётся и в теле (`version`, 64 hex-символа), и заголовком strong `ETag` — база optimistic save REQ-07. Ответ содержит `cache-control: no-store`. Внутренний symlink читается по реальному относительному пути (контракт resolver’а REQ-03); абсолютные пути хоста в ответе отсутствуют.

Frontend передаёт текст в Code Editor panel без format-on-load и без DSL round-trip. Поверхность — read-only code view (`<pre>`): textarea по спецификации HTML нормализует CRLF в LF в value, что нарушило бы критерий буквальности переводов строк; редактируемый buffer (Monaco) и dirty state — предмет REQ-06. Открытие файла — отдельный изолированный resource со своими loading/error (с retry) состояниями; ошибка открытия не ломает Files и Diagram. Новые upstream-зависимости не добавлены: `node:crypto` (sha256) и `node:fs/promises`.

## Границы REQ-07

REQ-07 замыкает write path: `PUT /api/files/*` принимает `{content, version}` и выполняет атомарную замену файла. Запись идёт через `saveWorkspaceFile` (`apps/server/src/workspace-file.ts`) — тот же guard `resolveExisting` REQ-03 (realpath цели), та же проверка regular file и тот же классификатор REQ-04, что у чтения и списка, поэтому список, чтение и сохранение не могут разойтись в правилах. Синтаксически битый JSON отклоняется content-type parser'ом Fastify ещё до хендлера и приводится к общему envelope `400 VALIDATION_ERROR`.

Conflict detection — optimistic по version token'ам: перед записью текущие bytes файла читаются заново, их sha256 сравнивается с присланным `version`; несовпадение даёт `409 CONFLICT` без единой записи в файл (не last-write-wins). Новый код ошибки `CONFLICT` добавлен в контракты; `saveFileRequestSchema` — literal string + sha256-подобный token, `saveFileResponseSchema` — то же представление, что у чтения (normalized path, новая version). Запрос и ответ дублируются заголовком `ETag` с `cache-control: no-store`.

Запись побайтовая: текст кодируется ровно в UTF-8 без нормализации, форматирования и DSL round-trip; NUL-байт и запрещённый классификатором тип дают `415 UNSUPPORTED_FILE` до записи. Атомарность — temp-файл `.likec4-save-<uuid>.tmp` в том же каталоге (rename в рамках одной файловой системы), `mode` копируется с исходного файла; при ошибке записи/rename temp удаляется и исходный target остаётся нетронутым (частичной записи не бывает). Успешный ответ содержит новую version — sha256 записанных bytes.

Frontend (`apps/web/src/panels/code-editor-panel.tsx`) хранит редактируемый buffer поверх сохранённого текста; Ctrl+S/Cmd+S с `preventDefault` сохраняет только активный ready/dirty файл и блокирует параллельный save. Отправляется buffer на момент вызова; race guard: если buffer изменился во время PUT, сохранённая база и version обновляются, но buffer и dirty пересчитываются от текущего ввода — пользовательский текст не теряется. Ошибка или конфликт не сбрасывают buffer и dirty; конфликт (`CONFLICT`) помечается отдельно с предложением перезагрузить страницу (явная перезагрузка файла — REQ-12/REQ-17). Статусы сохранения (`сохраняем…`, `конфликт записи`, текст ошибки) доступны (`role="status"`/`role="alert"`) рядом с метаданными файла. Reparse диаграммы после сохранения — REQ-17, в срез не входит. Новые upstream-зависимости не добавлены: `node:crypto`, `node:fs/promises` (writeFile/rename/rm/stat).

## Границы REQ-08

REQ-08 открывает write path для несуществующих файлов: `POST /api/files` принимает `{parent, name}` и создаёт ровно новый пустой `.c4`. `parent` — workspace-относительный путь существующего каталога (`''` — корень), `name` — строго базовое имя с суффиксом `.c4`: это подмножество классификатора REQ-04, поэтому созданный файл гарантированно попадает в дерево и открывается как редактируемый исходник, а «создать то, что нельзя открыть» невозможно. Имена с `/`, `\`, NUL, `.`/`..` и длиннее 255 байт дают `400 INVALID_PATH` (path-семантика во вложенном имени не допускается), иное расширение — `400 VALIDATION_ERROR`; обе проверки идут до любого обращения к fs.

Каталог назначения резолвится `resolveExisting` guard’а REQ-03 (realpath внутри workspace, отсутствующий parent — `404`, файл вместо каталога — `400 INVALID_PATH`), а цель — `resolveChild` того же guard’а: для уже занятого имени проверяется и realpath цели, поэтому symlink с именем нового файла наружу workspace даёт `403 PATH_OUTSIDE_WORKSPACE`. Неперезапись — `writeFile` с флагом `wx` (атомарный create-if-not-exists): существующий файл или каталог даёт `409 CONFLICT` без единого байта записи, а гонка двух одинаковых запросов завершается ровно одним успехом; исчезновение parent между resolve и записью — `404`, не 500. Создаётся пустой literal-файл; успешный ответ — `201` с тем же представлением `FileContentResponse`, что у чтения (`version` — sha256 пустого содержимого), заголовки `ETag` + `cache-control: no-store`. Контракт — `createFileRequestSchema`/`createFileResponseSchema` (`packages/contracts`); новых кодов ошибок и upstream-зависимостей нет (`node:fs/promises` stat/writeFile).

Frontend (`apps/web/src/panels/files-panel.tsx`) держит форму создания над деревом: каталог выбирается из записей `kind: directory` текущего ответа `GET /api/files` (пустой workspace — только корень, поэтому форма доступна и до появления первого файла), имя валидируется до запроса — `notes` дополняется до `notes.c4` с превью итогового пути (`role="status"`), а иное расширение или path-подобное имя отклоняются инлайн без API-запроса. После успеха дерево перечитывается из server state (локальной вставки нет — UI не расходится с сервером и не создаёт ложные записи), а файл сразу открывается в Code Editor по относительному пути. Ошибка запроса остаётся видимой рядом с формой (`role="alert"`), конфликту даётся отдельное понятное сообщение; дерево и редактор при ошибке не меняются. Включение нового файла в LikeC4-модель и diagram — reparse REQ-17, в срез REQ-08 не входит.

## Границы REQ-09

REQ-09 добавляет создание каталога: `POST /api/directories` принимает `{parent, name}` и создаёт ровно один новый каталог (`createWorkspaceDirectory`, `apps/server/src/workspace-file.ts`) — `mkdir` без recursion, поэтому произвольный путь не создаётся, parent обязан существовать. Имя валидируется общей с REQ-08 `validateEntryName` (пустое — `400 VALIDATION_ERROR`, `/`, `\`, NUL, `.`/`..`, длиннее 255 байт — `400 INVALID_PATH`) плюс отдельное правило каталогов: ведущая точка запрещена (`400 VALIDATION_ERROR`), потому что скрытый каталог невидим для фильтра дерева REQ-04 и нарушил бы критерий «после успеха новый каталог появляется в дереве»; расширение `.c4` в имени каталога, наоборот, допустимо — классификатор файлов к каталогам не применяется. Каталог назначения резолвится общим с REQ-08 `resolveParentDirectory` (отсутствующий parent — `404`, файл вместо каталога — `400 INVALID_PATH`), цель — `resolveChild` guard’а REQ-03, поэтому traversal, symlink-parent и symlink с именем цели наружу workspace дают `403 PATH_OUTSIDE_WORKSPACE` до записи. Неперезапись — сам `mkdir` (create-if-not-exists): занятое имя (файл или каталог) даёт `409 CONFLICT` без изменений на диске, исчезновение parent между resolve и записью — `404`, не 500. Успешный ответ — `201` c `{path, name, kind: 'directory'}` и `cache-control: no-store`; etag не отдаётся — у каталога нет содержимого и version token. Контракт — `createDirectoryRequestSchema`/`createDirectoryResponseSchema` (`packages/contracts`); новых кодов ошибок и upstream-зависимостей нет (`node:fs/promises` mkdir).

Дерево (`workspace-tree.ts`) научилось показывать пустые каталоги: обход возвращает признак «ни одной видимой записи», и такой каталог попадает в `GET /api/files` как directory-entry без детей (в т.ч. цепочка пустых каталогов видна целиком). Каталог, где после скрытых и нерелевантных записей не осталось разрешённых файлов, по-прежнему вырезается — ветки вроде `node_modules` не попадают в дерево; недоступный для чтения подкаталог тоже вырезается, а не выглядит пустым. Frontend (`apps/web/src/panels/files-panel.tsx`) держит вторую форму рядом с формой REQ-08 в общем контейнере действий: parent выбирается из каталогов текущего ответа `GET /api/files` (теперь включая пустые — созданный каталог сразу доступен как parent), имя валидируется до запроса — path-подобное имя и ведущая точка отклоняются инлайн без API-запроса, hint (`role="status"`) показывает итоговый относительный путь. После успеха дерево перечитывается из server state, но каталог не открывается в редакторе — открывать нечего; ошибка остаётся видимой рядом с формой (`role="alert"`), конфликту даётся отдельное понятное сообщение, дерево и редактор при ошибке не меняются.

## Границы REQ-14

REQ-14 включает загрузку полного multi-file LikeC4 проекта официальным API. Единственная новая upstream-зависимость — пакет [`likec4`](https://www.npmjs.com/package/likec4) **`1.59.4`** (exact, `apps/server/package.json`), тот же релиз, что зафиксирован в шапке (v1.59.4, commit 33dbc2d). Вызванный API — Node-only [`LikeC4.fromWorkspace(root, { logger: false, printErrors: false, throwIfInvalid: false })`](https://github.com/likec4/likec4/blob/v1.59.4/packages/likec4/src/LikeC4.ts) и методы экземпляра `getErrors()`, `computedModel()`, `views()`, `elements()`, `dispose()`; библиотечный вход пакета не импортирует CLI-зависимости (playwright, yargs, nano-spawn), а `playwright` в дереве не имеет postinstall-скрипта и браузеры не скачивает. Интеграция не зависит от Git.

Загрузка — `loadWorkspaceProject` (`apps/server/src/workspace-project.ts`): корень приходит из `trustedRoot()` resolver’а REQ-03 (realpath), клиентский путь не участвует — `LikeC4.fromWorkspace()` сам рекурсивно находит и парсит все `*.c4`/`*.likec4` проекта (правила discovery версии 1.59.4: рекурсивный скан каталога, default exclude `**/node_modules/**`, `name` в `likec4.config.json`), поэтому открытие одного файла в editor не сужает parsing context. `watch` и `mcp` выключены (вочеров и процессов нет), WASM-graphviz ленив и при отсутствии layout-вызовов не загружается. `dispose()` вызывается в `finally` каждого запроса. Кэша результатов нет — каждый запрос парсит workspace заново (семантика reparse — REQ-17); `LocalWorkspaceProvider` выполняет только single-flight: параллельные запросы делят одну загрузку, promise очищается по завершении.

`GET /api/project` (контракты: `projectResponseSchema`) отдаёт дискриминированный ответ: `{status:'ok', views[{id,title}], elements[{id,kind,title}]}` при пустом `getErrors()` либо `{status:'invalid', diagnostics[{message, path?, range}]}` при хотя бы одной ошибке парсинга. Половинная модель при ошибках не отдаётся — REQ-15/18 не должны принимать устаревшую диаграмму за актуальную. Списки отсортированы по `id`. Диагностика не раскрывает пути хоста: `sourceFsPath` превращается в workspace-относительный `path` (вне корня поле опускается), вхождения абсолютного корня в `message` заменяются. Поведение версии 1.59.4 отражается как есть: если проект не определяет view с id `index`, в `views` появляется implicit `index` «Landscape view»; view с некорректным predicate молча исключается из `views()`; пустой workspace даёт `ok` с пустыми массивами; multi-project workspace (несколько `likec4.config.json`) — документированное ограничение MVP: upstream бросает ошибку, endpoint отвечает общим 500 `INTERNAL_ERROR`. `toDSL()`/`writeDSL()`/`format()` из того же пакета сознательно не вызываются: сериализация распарсенной модели обратно в DSL запрещена границами MVP.

## Границы REQ-15

REQ-15 подключает интерактивный preview официальным integration path — субпаф [`likec4/react`](https://github.com/likec4/likec4/tree/v1.59.4/packages/likec4/react) пакета [`likec4`](https://www.npmjs.com/package/likec4) **`1.59.4`** (тот же релиз, что REQ-14; зависимость объявлена и в `apps/web/package.json`, рядом `@likec4/core` **`1.59.4`** для официальной фабрики клиента). Отдельный npm-пакет `@likec4/diagram` не устанавливается: `likec4/react` — опубликованный самодостаточный бандл того же `@likec4/diagram` v1.59.4 (внешние импорты — react/react-dom/`@likec4/core`/immer), его стили инжектируются в ShadowRoot и не конфликтуют с IDE. Используются публичные `LikeC4ModelProvider` + `ReactLikeC4` (`pannable`, `zoomable`, `controls`, `fitView`, `onNavigateTo`). Адаптированного upstream-кода нет: компоненты подключаются как есть, вся интеграция — конфигурация; самописный renderer отсутствует.

Путь данных: `LikeC4.fromWorkspace()` → `layoutedModel()` (layout graphviz-wasm, загружается лениво) → `$data` (`LayoutedLikeC4ModelData` — чистый JSON, переживает побайтовый `JSON.parse(JSON.stringify())` round-trip) → `GET /api/diagram` → `LikeC4Model.create()` (`@likec4/core/model`) → `LikeC4ModelProvider` → `ReactLikeC4 viewId`. Модель передаётся как opaque JSON: zod (`diagramResponseSchema`) проверяет только конверт (`_stage:'layouted'`, `projectId`, непустой `views`-объект), структурную целостность гарантирует официальная пара create+render; серверный тест дополнительно прогоняет JSON round-trip через `LikeC4Model.create()` — CI-страховка совместимости формата клиент/сервер без браузера.

`loadWorkspaceDiagram` (`apps/server/src/workspace-diagram.ts`; общий хелпер диагностики вынесен в `workspace-diagnostics.ts`) повторяет порядок REQ-14: `getErrors()` проверяется ДО layout — при повреждённом DSL `layoutedModel()` всё равно вернул бы половинную модель с implicit view, поэтому ответ — `{status:'invalid', diagnostics}` без модели и без `views`; 0 views → `{status:'empty', reason:'NO_VIEWS'}`; иначе `{status:'ready', model, views, defaultViewId}`. `defaultViewId` — детерминированное правило: view `index` (implicit «Landscape view» либо явная), иначе лексикографически первая; выбор view из списка — REQ-16. Список `views` продублирован из `/api/project` сознательно: он нужен Diagram panel для внутренней навигации, а `/api/project` frontend не вызывает. Single-flight без кэша, отдельный от `projectLoad` (двойной парсинг при вызове обоих endpoints — задокументированное ограничение); layout выполняется на каждый запрос, размер ответа растёт с проектом — ограничения MVP (reparse после save — REQ-17). Ошибка layout (wasm) даёт общий 500 `INTERNAL_ERROR` без раскрытия путей хоста.

Renderer загружается отдельным lazy-чанком (~2.3 МБ, gzip ~0.7 МБ) только при готовой модели. Ошибки renderer'а и `LikeC4Model.create()` ловит `DiagramErrorBoundary` (`apps/web/src/diagram/`) — единственный class-компонент приложения: fallback показывает сообщение и кнопку «Повторить» (remount renderer'а без нового API-запроса). Панель различает loading / error (транспорт, retry) / empty / invalid / ready; ошибка preview не влияет на Files и Code Editor. Внутренняя навигация preview (`onNavigateTo`) переключает view локально в рамках уже полученной модели; `.diagram-host` даёт react-flow контейнер определённой высоты (flex + `min-height: 0`).

## Границы REQ-16

REQ-16 делает выбор диаграммы пользовательским. Сервер и контракты не меняются: `GET /api/diagram` уже отдаёт полный список `views[{id,title}]` и `defaultViewId` (REQ-15), новых upstream-зависимостей нет — срез чисто клиентский.

Diagram panel (`apps/web/src/panels/diagram-panel.tsx`) показывает селектор всех views модели: список строится из ответа (не из имён файлов и не из константы), option label — `title` view, при отсутствии title — её id; серверное правило default (implicit `index`, иначе лексикографически первая) остаётся выбором без пользовательского действия. Выбор в селекторе переключает `ReactLikeC4 viewId` в рамках уже загруженной layouted-модели — нового API-запроса не возникает; внутренняя навигация preview (`onNavigateTo`) и селектор пишут в одно состояние, поэтому клик по элементу диаграммы обновляет и селектор.

Selection переживает обновление двумя механизмами. Внутри сессии — React state: перезагрузка `/api/diagram` (кнопки «Повторить», будущий reparse REQ-17) не сбрасывает выбранную view, пока она существует в новом списке. Между загрузками страницы — URL hash `#view=<id>` (`apps/web/src/diagram/view-selection.ts`): hash восстанавливается при монтировании, а каждое фактическое показанное view записывается туда `history.replaceState` (без засорения history навигацией между views); ссылка на конкретную диаграмму shareable. Значение hash — только id view из ответа модели, не путь файла.

Fallback при исчезновении выбранной view: если после загрузки модели выбранного id нет в списке, показывается серверский `defaultViewId` и заметка (`role="status"`) «View «…» больше не существует в модели — показана view «…»»; сброс выбора не выдаёт отсутствующую view за актуальную. Заметка закрывается следующим осознанным выбором. Состояния invalid/empty скрывают селектор (списка views в ответе нет), вместе с ним — заметку. Интеграционные проверки — `apps/web/src/app.test.tsx` (describe REQ-16): полный список views с названиями, переключение двух views без нового запроса, отражение внутренней навигации, сохранение selection после перемонтирования (page refresh), fallback с заметкой при исчезновении view.

## Границы REQ-19

REQ-19 использует опубликованный browser language server [`@likec4/language-server` **1.59.4**](https://www.npmjs.com/package/@likec4/language-server), `monaco-editor-wrapper` **6.7.0**, `monaco-languageclient` **9.6.0**, `@typefox/monaco-editor-react` **6.7.0** и `@codingame/monaco-vscode-*` **16.1.1**. Версии соответствуют LikeC4 `v1.59.4` (commit `33dbc2d`). `apps/web/src/editor/likec4-language-config.ts` — адаптация official Playground config: локальный Vite worker `@likec4/language-server/browser-worker?worker` (ES module worker), `RegisteredFileSystemProvider` overlay, TextMate grammar и language configuration как VS Code extension, `openEditorFunc` переиспользует единственный editor. `codeResources` не используется (как и в Playground): моделями управляет приложение. Статические assets в `apps/web/src/editor/upstream/` побайтово идентичны `apps/playground/likec4.tmLanguage.json` и `apps/playground/language-configuration.json` того же commit (MIT provenance).

Единственный источник Monaco-инстанции — `@codingame/monaco-vscode-editor-api` (`apps/web/src/editor/likec4-monaco.ts`); raw `monaco-editor` не устанавливается, потому что рядом это второй независимый экземпляр Monaco. Внутренние URI моделей имеют вид `file:///relative/path` и обозначают только browser memory workspace: ни absolute host path, ни путь, присланный браузером, туда не попадает. При первом открытии LikeC4 source frontend читает весь разрешённый набор `.c4`/`.likec4` через существующие `GET /api/files` и `GET /api/files/*` (параллелизм — четыре запроса), регистрирует файлы в overlay filesystem, создаёт Monaco-модели и отправляет серверу `BuildDocuments.req` со списком URI. Активный файл повторно не читается; config JS/TS не загружается для выполнения и не исполняется. Существующие Monaco модели не перезаписываются (dirty buffer приоритетнее первоначального текста API), а правки write-through'ятся в memory filesystem (`updateSource`); browser не имеет endpoint записи и не вызывает `toDSL()`, `writeDSL()` или `format()`.

Monaco API не вызывается до инициализации VS Code services: standalone-вызов (например, `createModel`) запускает собственную инициализацию и ломает последующую инициализацию wrapper’а («Services are already initialized»). Поэтому `likec4-language-runtime.ts` откладывает создание моделей до `attachWrapper` (вызывается из `onLoad` `MonacoEditorReactComp`), а повторное монтирование компонента создаёт новый конфиг (новый worker и provider). По этой же причине `main.tsx` не оборачивает app в `StrictMode`.

Official language client даёт syntax highlighting (TextMate grammar + тема Default Dark+), autocomplete и diagnostics: сервер публикует их стандартным `textDocument/publishDiagnostics`, vscode-languageclient превращает их в Monaco markers, runtime читает `getModelMarkers`/`onDidChangeMarkers` и дублирует доступным списком только для активного документа. Приложение не добавляет самодельные parser/grammar/completion provider. Невалидный документ и ошибка фоновой загрузки другого source остаются неблокирующими: Monaco можно продолжать использовать и переключать на другой файл; кнопка «Повторить language service» перезапускает клиент (`restartLanguageClient` + повторный `BuildDocuments`). `GET /api/project` намеренно не является источником editor diagnostics, поскольку он анализирует только сохранённый disk workspace. WebSocket bridge, локальный CLI и локальная LikeC4 extension пользователю не требуются.

Dev-режим Vite обязан prebundle'ить CJS-зависимости, достижимые из сырого browser-графа language server'а (`p-queue`, `eventemitter3`, `word-wrap`, `picomatch`, `strip-indent`, `indent-string` и LSP-пакеты в `optimizeDeps.include` `apps/web/vite.config.ts`), иначе ES module worker умирает на «does not provide an export named 'default'»; `worker.format: 'es'` обязателен. Production bundle содержит chunk ~9 МБ (language server + Monaco) — сознательный размен за official integration без серверной установки.
